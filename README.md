# IPRC1000 按键映射（Windows 桌面程序）

把 Verizon FiOS 的 IPRC1000 蓝牙语音遥控器（Broadcom BCM20734，VID `0A5C` / PID `8502`）
变成 Windows 上的快捷键盘。按键全部可自定义，语音键按下时按住一个「说话键」给输入法用。

## 怎么用

双击 **`dist\IPRC1000-win32-x64\IPRC1000.exe`**（或 `run.cmd`）。

窗口里就是一张遥控器图，点哪个键改哪个键：

1. 按一下遥控器任意键把它唤醒，标题栏的状态点变绿；
2. 在图上**点你要改的那个位置**（比如「静音」），右边面板显示它的绑定和当前动作；
3. 选一个预设，或者点「录制快捷键」用**电脑键盘**按组合键；也可以直接粘一段文字；
4. 点「保存」。这个位置在图上变成蓝底，表示已经改过键。

图是**照着真机照片画的**，三列按钮，从上到下：

| 位置 | 按键 |
| --- | --- |
| 顶部 | 左边是麦克风开孔（不是按键），右边 `pwr` 电源 |
| 第 1 排 | `back` / `∧` 上 / `menu` |
| 第 2 排 | `|◀` 左 / `ok` / `▶|` 右 |
| 第 3 排 | `exit` / `∨` 下 / `info` |
| 第 4 排 | 爱心（收藏）/ 话筒（语音）/ 人头（我的） |
| 第 5 排 | 快退 / 播放暂停 / 快进 |
| 第 6 排 | `VOL` 音量摇杆 / 静音 + `last` 上一频道 / `CH` 频道摇杆 |
| 底部 | logo |

**图上位置和真实按键的对应关系**出厂只预填了已实测确认的 6 个（语音、上、下、左、右、OK，
蓝底），其余 16 个是灰色空壳。

### 一次性绑定剩下的按键（推荐用向导）

点右上角 **「依次绑定剩下的 16 个键」**，它会从最上面那个空位开始：

1. 图上高亮一个键，顶上提示「第 3 / 16 个 —— 请按一下遥控器上的『菜单』键…」；
2. 你按一下遥控器上对应的键，它自动跳到下一个，不用再点；
3. 按错了（按到一个已经绑过的键）会被拒绝，提示「这个键已经绑在『上』了」，可以重按；
4. 某个键暂时不想绑就点「跳过」，`Esc` 或「取消」随时退出。

绑完按钮会变成「全部按键都已绑定」。

也可以一个一个来：点那个位置 → 点「按键确认」→ 按一下遥控器上对应的键
（图上那一格会开始虚线跳动等待）。绑错了点「解绑」重来；
右上角「重置全部」只清动作，清掉绑定关系用「解绑」。

图例：**蓝底**=已改键；**灰底+琥珀圈**=已绑定但还没设动作；**浅灰虚线**=还没绑定。

图上没归位的按键（比如固件补发的幽灵键 `0x17`、用户自己加过 `0x12 → Win+D`）
会列在右下角，点一下同样能改动作。
所有配置存在 `config/keymap.json`（动作）和 `config/layout.json`（位置绑定）。

> 录制只认**电脑键盘**。遥控器自己的键不参与录制（接管模式下它给的是扫描码，不是虚拟键码，
> 记下来 `SendInput` 也复原不了）。遥控器的键要用什么行为，用预设按钮或「按键确认」+ 录制。
>
> 打包版的配置放在 **exe 同级**的 `dist\IPRC1000-win32-x64\config\`（重新打包不会覆盖它）；
> 用 `npm start` 开发时用的是根目录的 `config\`。

## 语音转文字（按住遥控器语音键，说的话直接上屏）

三步，第一次配好以后就只剩第 3 步。

**① 让电脑把遥控器当麦克风**

面板右上角有一行 **「语音桥接」**：

- 显示「未启动」就点右边那个 **「启动」**，会弹一个 UAC，点「是」；
- 变成 **绿点 + 运行中** 就好了，会开一个黑窗口显示电平（说话时能看到数字跳动）。

这一行做的是：用 ETW 抓蓝牙 HCI 报文 → 解出 PCM → 播进虚拟声卡 `CABLE Input`，
于是系统的录音设备 **`CABLE Output` 就等于遥控器麦克风**（它已经设成默认录音设备了）。

> 不想用面板按钮的话，双击 `mic-live.cmd` 效果一样。它要管理员权限是因为 ETW 必须提权。

**② 把语音键设成「语音输入 Win+H」**

在图上点那个**话筒**图标 → 右侧预设里选 **「语音输入 Win+H」** → 保存。
（出厂就给你设好了，除非你自己改过。）

**③ 用**

1. 鼠标点进要输入文字的框（聊天框、记事本、搜索框都行），光标在里面闪；
2. **按住**遥控器上的语音键，等半秒左右（Windows 语音输入栏弹出来需要一点时间），说话；
3. 说完**松开**，文字就出现在框里了。

要点：

- Win+H 是 Windows 自带的语音输入，**需要联网**；第一次用可能要同意一下隐私条款；
- 它认的是**默认录音设备**，所以 `CABLE Output` 必须是默认（本机已是）；
- 说完一句可以接着说，它会自己断句；再按一次语音键或按 `Esc` 关掉；
- 如果语音输入栏弹出来了但一个字都不出，先看那个黑窗口的电平有没有跳动：
  **没跳动 = 桥接没抓到音频**（多半是没提权 / ETW 没起来），有跳动 = 桥接正常，是识别那边的问题。

> 另一条路：预设里的「语音：按住 Ctrl+Win」「语音：按住右 Alt」是给支持**按住说话**的输入法用的
> （按下按住、松开释放）。你的输入法没有这个快捷键就别选它。

**能不能用 WorkBuddy 自带的那个语音键？**

能，但它只在自己窗口里管用。WorkBuddy 的语音输入绑在「设置 → 键盘快捷键 → **语音录制**」上，
Windows 默认是 **Ctrl+D**（另有一个「按住 Alt」的变体），所以预设里给了 **「语音输入 WorkBuddy（Ctrl+D）」**。

差别在这里：

| | 生效范围 | 说话时 | 文字进哪儿 |
|---|---|---|---|
| Win+H（`dictate`） | **全局**，任何程序 | 弹 Windows 语音栏 | 当前光标处 |
| WorkBuddy（`dictate_wb`） | **只在 WorkBuddy 窗口前台时** | 输入框里直接出字 | 只进 WorkBuddy 聊天框 |

也就是说，想给 Word、浏览器、微信说话，只能用 Win+H；只想对着 WorkBuddy 聊天框说话，Ctrl+D 那条更顺手。
两条都吃同一个声源，所以上面第 ① 步（语音桥接）照样要开着。

> 如果「键盘快捷键」里搜不到「语音录制」，说明这个功能没对你的账号开放（服务端灰度开关），那就只能用 Win+H。

## 万一键盘/鼠标不对劲（重要）

接管模式是在驱动层拦按键，所以它出问题时症状很吓人：**键盘像死了、按键乱跳、鼠标点击也跟着怪**。
下面三条任意一条都能立刻恢复：

1. **面板右上角「紧急停止接管」** —— 一键撤掉过滤器，按键全部还给系统（这个窗口本身还能点，鼠标是好的）。
2. **托盘图标右键 → 紧急停止接管** —— 窗口被挡住了就用这个。
3. **双击 `stop.cmd`** —— 直接杀掉程序，最粗暴也最有效。

如果停了还不正常，就是有修饰键被卡住了（Ctrl/Win 一直处于按下状态），按一下对应的物理键就能释放；
再不行就拔插一次 USB 接收器。

**程序自己也带了两道刹车，正常不会走到需要你手动救的地步：**

- 每收一个按键都会核对「这个设备号还是不是遥控器」，只要硬件 ID 变了立刻缴械（因为设备号会被复用）；
- 1.2 秒内出现 6 个以上不同扫描码就判定为「人在打字」（遥控器一次只按一个键），立刻缴械。
  缴械后日志会打印 `⚠ 接管模式已自动停用：…`，10 秒后自动重试接管。

历史事故：2026-11-10 出现过一次「键盘鼠标都失灵、按键乱」——
根因是遥控器休眠后它的设备号（7 号）被别的键盘占用，程序继续按号吞键；
顺带发现匹配遥控器用的正则写成了 `0A5C|8502`（或），串号里带 8502 的设备也会被误认。
两处都已修掉：匹配改成「VID 必须是 0A5C **且** PID 必须是 8502」，并加了上面两道刹车。

### 2026-11-11：满屏 mmmmmm，语音键像被看不见的手按着

现象：不说话也会隔几秒冒出一个 `m`，日志里 `0x32` **每 6.0 秒来一次**，一直不停。

日志（`resources/app/out/app.log`）里是两个问题叠在一起：

1. **蓝牙断开重连之后，接管没有重新抢回来。**
   顺序是 `遥控器已断开` → `接管模式不可用：没有找到遥控器键盘设备` → `遥控器已连接`，
   然后**再也没有**出现 `▶ 接管模式已启用`。因为失败分支把 `interceptTried` 置真之后
   再也不复位，重连分支又只认 `sourceKind === 'intercept'` 才重置。
   于是永远停在 Raw Input：按键照常打进窗口（就是那个 m），我们还照旧派发一次。
2. **遥控器自己在连发。** 语音键开麦之后如果没被正常收尾，固件会每 6 秒重发一次这个键，
   每一发都是一次 Win+H。人按不出 6.0 秒的硬周期 —— 这就是「机器在发」的指纹。

改了三处（`src/app.js`、新增 `src/stuck.js`）：

- 设备重新出现时**无条件**重置接管状态，另加 2 秒一次的**接管看门狗**（连续失败退避，最长 1 分钟一次）；
- **卡键静音**：同一个键以几乎相同的间隔（抖动 < 350ms）连发 4 次就判定是机器在发，
  这个键暂停 30 秒，期间一个键都不注入。判定逻辑在 `src/stuck.js`，
  `node scripts/test_stuck.js` 有单测（机器周期要抓到、人手连点不能误判）。
  面板会弹红条，点「遥控器已恢复，解除暂停」立刻放行；
- **紧急停止真的停了**：以前它只撤接管，Raw Input 还在派发，所以点了停止 Win+H 照样往外冒。

让遥控器本身停下来的办法：**取下电池再装回**（等于给它断电复位）。

### 那两颗灯是什么意思

- **按语音键时亮红灯**：正常。红灯 = 麦克风正在工作，松手就灭。
- **装电池时亮一下绿灯**：正常。那是开机 / 进配对状态的自检灯，闪一下完事。

所以这两颗灯本身**不代表连接失败**。只看两个反常情况：

| 看到的现象 | 含义 | 怎么办 |
|---|---|---|
| **没按**语音键，红灯却亮着 | 语音键卡在「开麦」状态，就是上面的连发 | 取下电池再装回 |
| 绿灯**一直闪**不停 | 它认为自己没配对，正在找主机 | 设置 → 蓝牙和其他设备 → 重新配对 |

### 同一天晚上：按一下语音键就「卡死」

日志（`resources/app/out/app.log`）是这样的，最后一条之后就彻底安静了：

```
19:12:33  按键 0x24 → Win+L          ← 上一个频道
19:12:36  按键 0x12 → Win+D          ← 收藏
19:12:37  按键 0x12 → Win+D
19:12:42  按键 0x32 → Win+H          ← 语音
（之后什么都没有）
```

程序本身没崩：进程还在、CPU 空闲、`/api/app` 照常响应、`explorer` 也正常。
所以问题不在「程序挂了」，而在**注入出去的 Win 键**和**接管线程**这两处：

1. **组合键被一口气塞进同一个 `SendInput` 调用。**
   Windows 外壳按「输入拍」处理 Win 键，`Win↓ H↓ H↑ Win↑` 四件事挤在同一拍里，
   它可能把「按下+抬起」当成同一拍处理，于是 Win 留在按下状态 ——
   所有快捷键失灵、开始菜单乱弹，体感就是「卡死」。
   现在按真键盘的节奏来：每步 10ms 分开送，末尾再补一遍抬起（重复发抬起无害）。
   逻辑抽成了纯函数 `comboPlan()`，`node scripts/test_combo.js` 盯着顺序。

2. **接管线程可能卡在系统调用里。**
   以前的内层 `interception_receive` 是阻塞的，队列一空就永久挂在那儿：
   过滤器还挂在设备上、却没人读报文，**遥控器就整个哑掉**（按键全被吞，连方向键都不动）。
   现在：
   - 接收循环改成单层 `waitTimeout(250ms)` 驱动，永远出得来；
   - 线程每 ≤1 秒发一次心跳，主线程 4 秒收不到就**销毁上下文自动重建**；
   - 线程死亡会上报（以前被 `settle()` 的一次性判断吞掉了，主线程还以为一切正常）。

3. **急停之后不用重启**：顶栏多了一个「重新接管」按钮（只在需要时出现），
   销毁旧上下文、重新抢一次接管，顺手把急停状态清掉。

遥控器按了没反应时的自救顺序：**点「重新接管」 → `stop.cmd` 重开 → 取下电池再装回**。

### 「按一下变成按了好几次」是怎么来的

把今天（19:42–19:47）的日志按时间戳排开，同一个键的间隔是这样的：

```
19:43:08.862  0x32 → Win+H
19:43:14.866  0x32 → Win+H      +6.004s
19:43:20.873  0x32 → Win+H      +6.007s   ← 判定卡住，静音 30 秒
19:43:50.897  0x32 → Win+H      （静音刚到期，下一发就进来了）
19:43:56.974  0x32 → Win+H      +6.077s
19:44:03.003  0x32 → Win+H      +6.029s
```

**6.000 秒，抖动只有几毫秒，能持续五分钟以上。** 人手按不出这种节奏。
也就是说：遥控器的语音键按下去之后并没有「抬起」，它进入了一个开麦状态，
然后每隔 6 秒把同一个按键报文重发一次，等主机回应 —— 而 Windows 从头到尾
不知道这台设备有麦克风（音频走的是它自己的私有蓝牙通道），所以这个回应永远不会来。

另外，真正按下的那一瞬间有时会连着来两份（实测间隔 45 / 46 / 62 / 77 / 95 / 109 ms），
是固件在开麦握手时又补发了一次。

两者叠加，你按一下，程序就当成按了 2 次、然后每隔 6 秒再按一次。

程序这边能做的只有「认出来、别派发」，所以现在：

- 同一个键 **3 次**、间隔一样齐（抖动 < 350ms、且每次至少隔 0.8 秒）→ 判定卡键；
- 立刻静音这个键 **30 秒**；再犯就 60 秒 → 120 秒 → 封顶 15 分钟（十分钟不犯自动清零）；
- 静音期间一个键都不注入，也不会在日志里刷屏。

> 至于「为什么那 6 秒停不下来」，要先分清是谁在发：**关掉程序**，等一分钟，
> 看屏幕上还会不会自己冒 `m`。会 → 是遥控器/蓝牙在重发，跟程序无关；
> 不会 → 那就是程序这边的问题，回来找我。

**实测结果：关掉程序之后 `m` 照样自己冒 —— 是遥控器/链路在重发。**

于是又发现程序这边一个帮凶：`held` 的静默兜底是 **5 秒**，而这个重发周期是 **6.000 秒**。
当设备漏发「抬起」（这正是现在的情况），5 秒一到程序就把键当「已松开」清掉，
紧接着 6 秒那一发重发就被判成「又按了一下」—— 一次按压被拆成一串。
现在改成：重发会刷新时刻、兜底时间提到 **12 秒**（重发周期的两倍）。

规则抽在 `src/latch.js`，`node scripts/test_latch.js` 专门盯这件事：
模似「一次按下 + 之后每 6 秒一发、始终没有抬起」，11 发必须只算 1 次。


## 双击了没反应？

程序是**单实例**的：已经有一个在跑时，第二次双击会去把那个窗口叫出来，然后自己安静退出。
如果桌面和任务栏都找不到窗口，多半是上一次异常退出留了残留进程：

```cmd
stop.cmd
```

然后再双击一次。`stop.cmd` 会 `taskkill` 掉所有 `IPRC1000.exe`。
（排查时我踩过一次：后台起了 5 个残留进程把单实例锁占着，之后每次启动都「秒退、啥也不显示」。）

## 麦克风：为什么这么难

先说结论——**它的麦克风不走任何标准音频通道**：

- HID 只暴露一个键盘集合（Generic Desktop / Keyboard），没有音频端点，也没有 HFP。
- 音频和按键**走同一条 L2CAP 通道**（动态 CID `0x40/0x41`，就是 Windows HID
  驱动独占的那条 HID 控制/中断通道）。

这带来两个直接后果：

1. 用户态**没有任何 API 能订阅**这条通道 —— 它被 HID 驱动独占了。
2. 它也不在 HID 报文层，所以 `Interception` 那一层同样看不到。

**唯一的路是绕过整个蓝牙栈，在 HCI 层旁路抓包**：用 ETW 监听 BthPort 的原始 HCI
流量，自己把 L2CAP 分片重组成完整 PDU，再剥掉帧头拿到 PCM。

### 帧格式（逐字节实测确认）

```
L2CAP 负载 653 字节：
[0..12]   13 字节帧头   A1 F7 01 <seq> 00 <roll> <n> <cnt> 00 00 00 40 01
[13..652] 640 字节音频 = 320 个 16bit LE 样本 @ 16 kHz（20ms 一帧）
```

`<seq>` 逐帧 +1（1 字节回绕），可以用来**测量**丢帧而不是猜。
ACL 上常见拆两片，但**切片方式不固定**，必须按 PB 标志 + L2CAP 声明长度重组。

### 为什么默认抓不到

`HKLM\SYSTEM\CurrentControlSet\Services\BthPort\Parameters` 里有两个键是元凶：

| 键 | 默认 | 问题 |
|---|---|---|
| `EtwDropLargeEvents` | **1** | **大的 HCI 包直接丢掉** —— 音频一帧都进不来 |
| `MaxEtwBytes` | 小 | 单包会被截断，只剩半帧音频 |

所以必须先改注册表**并重启**（BthPort 在驱动加载时才读这两个值）。

### 操作顺序

```cmd
:: ① 管理员运行，改 BthPort 的 ETW 参数
enable-mic-capture.cmd
:: ② 重启电脑（必须，驱动加载时才读）
:: ③ 管理员运行，抓 20 秒并判定有没有声音
mic-test.cmd
```

`mic-test.cmd` 会指示你按住语音键说话，结束后自动分析 WAV 的峰值/RMS/有声占比，
直接告诉你「抓到声音了」还是「全是静音」。生成的文件在 `out/mic.wav`，双击就能听。

### 实时监听（已打通）

```cmd
mic-live.cmd
```

双击后（会请求管理员）按住语音键说话，声音会**实时从电脑扬声器出来**。
这条链路已经用合成音频验证过：`CLEAR` → 100 个音频包 → `END`，
电平计算与注入幅度完全吻合（0.3 幅度 × 0.6 增益 = −14.9 dBFS）。

```
ETW 抓 HCI → 重组 L2CAP → 剥 13 字节帧头 → 16k 上采样到 48k → 播放
```

- `tools/etw_consumer.exe --udp 127.0.0.1:31680`：抓包并推 PCM
- `scripts/mic_live.py`：收 UDP 并播放（`sounddevice` / WASAPI，可指定设备）

想换输出设备：

```cmd
mic-live.cmd list                       :: 列出所有输出设备
mic-live.cmd --device Realtek --gain 2  :: 指定设备 + 放大
```

### 变成系统「麦克风」（最后一步）

现在声音只到了扬声器。要让它成为输入法能用的录音设备，需要一个**虚拟声卡**。
本机原本没有（只有 Realtek + Intel SST），安装包已经准备好：

```cmd
install-vbcable.cmd        :: 提权后打开官方安装器，点 "Install Driver"
:: 装完重启
mic-live.cmd               :: 会自动检测到虚拟声卡并输出到它
```

链路：

```
遥控器麦克风 → ETW → mic_live.py → CABLE Input（播放设备）
                                        ↓  （驱动内部回环）
输入法录音设备选 CABLE Output（录音设备）→ 文字上屏
```

`mic-live.cmd` 不带参数时会**自动找 `CABLE Input`**：

- 找到 → 输出到虚拟声卡（输入法就能收到）
- 没有 → 输出到系统默认（就是你现在听到的扬声器）

想同时自己听到，加 `--device Realtek`。设备清单用 `mic-live.cmd list`。

> VB-CABLE 来自 [vb-audio.com](https://vb-audio.com/Cable/)，免费（donationware），
> 官方要求「以管理员身份运行 Setup，装完建议重启」。卸载：控制面板里卸掉 VB-Audio Virtual Cable。



## ⚠️ 核心问题：它会往窗口里打字

这颗遥控器的 23 个键发的是**标准键盘扫描码**，所以默认情况下每个键都会往当前窗口打字：

| 扫描码 | 打出的字符 | 键位 |
|---|---|---|
| `0x50 / 0x48 / 0x4B / 0x4D` | ↓ ↑ ← → | 方向键 |
| `0x1C` | Enter | OK |
| `0x32` | **m** | 语音键（按住会刷一屏 m） |
| `0x2B` | `\` | ? |
| `0x17` | i | **幽灵键**：几乎每按一次键，80–400ms 后都会跟着补发一次 |

### 两条走不通的路（已实测，不用再试）

1. **换驱动成「符合 HID 标准的设备」→ 无效。**
   换完之后 `ReadFile` 依然返回 `0x5 拒绝访问`。
   原因：Windows 对顶层集合为「键盘/鼠标」的 HID 设备**在 HID 类驱动层**就禁止了普通进程读报文，
   这跟下面绑的是 `kbdhid` 还是通用 `HID-compliant device` 完全无关。
   而且「删除设备 + 重新配对」还会把这个改动丢掉。

2. **低层键盘钩子（WH_KEYBOARD_LL）→ 做不到。**
   钩子拿不到按键来自哪台设备，吞掉遥控器的 `m` 会连你的物理键盘一起吞。

结论：**要让按键不打字，只能在键盘类驱动栈里加过滤层。**

### ✅ 正确方案：接管模式（Interception 驱动）

[Interception](https://github.com/oblitum/Interception) 是一个签名的键盘/鼠标过滤驱动，
它插在 `kbdclass` 栈里，能**按设备**把按键拦下来（不转发即等于吞掉），
再配合硬件 ID 只拦遥控器那一台，物理键盘完全不受影响。

它跟之前那次「换驱动」有本质区别：**它不改变设备绑定的驱动**，
设备仍然是 `kbdhid`，卸载即完全复原，不会让遥控器从蓝牙里消失。

安装（一次性，需要管理员）：

```
右键 enable-clean-mode.cmd → 以管理员身份运行
```

**然后重启一次**（它是上层过滤驱动，要随键盘设备栈一起加载）。

装好之后重启本程序，日志出现：

```
▶ 接管模式已启用（设备 #N）
  遥控器按键已被驱动层拦下，不会再往窗口里打字
```

面板顶部也会显示 `接管模式（按键已被拦下，不会打字）★`。

想复原：右键 `disable-clean-mode.cmd` → 以管理员身份运行。

### 已知安装故障：`Could not write to \system32\drivers`

这是官方安装器的一个 bug，会出现在部分 64 位系统上：

`install-interception.exe` 是 **32 位**程序（它内部会调
`Wow64DisableWow64FsRedirection`），在这台机器上它拿到的系统目录是**空字符串**，
于是把路径拼成了 `\system32\drivers\keyboard.sys`（**没有盘符**），写入失败。

失败之后是「半个安装」状态，非常容易误判：

| 项目 | 结果 |
|---|---|
| `keyboard.sys` / `mouse.sys` | ✅ 已经拷进 `System32\drivers`，签名有效 |
| 键盘类 `UpperFilters` | ✅ 已经加了 `keyboard` |
| `keyboard` / `mouse` 服务键 | ✅ 建好了，但 **`ImagePath` 是空的** |

没有 `ImagePath` 的服务永远加载不了，所以 `create_context` 一直返回 NULL。

修复：

```
右键 repair-interception.cmd → 以管理员身份运行 → 重启
```

它只补 `ImagePath`（以及缺的 `UpperFilters`），不重装、不覆盖别的值。
`enable-clean-mode.cmd` 现在也会在安装器返回非 0 时自动调用它。


| | 接管模式 ★ | 直读模式 | 观察模式（默认） |
|---|---|---|---|
| 前提 | 装了 Interception 驱动 | 驱动换成 HID 标准设备（**无效**） | 无需安装 |
| 会往窗口打字吗 | **不会** | — | **会** |
| 幽灵键能拦掉吗 | **能** | — | 只能忽略，字还是打出去了 |
| 语音键能按住吗 | **能，安静** | — | 按住会刷 mmmmm |

### 关于「系统原生」这个动作

接管模式会把按键全部吞掉，所以默认键位表里方向键和 OK 标的是 **`系统原生`**：
命中的键会在驱动层**原样转发回去**（把原始报文 `interception_send` 回键盘栈），
所以 ↑↓←→ 和 Enter 照旧生效，只是不再有「遥控器打一遍 + 我们注入一遍」的重复。

其它动作（组合键 / 粘贴文本 / 不执行）则完全按你的设置执行，不会再有多余字符。



`按住说话` 目前注入的是触发键，输入法会去录**电脑默认麦克风**。
要让遥控器自己的麦克风出声，需要先确定它把音频送去了哪里，再在蓝牙驱动层拦下来
（已知可行路线是 BthPort 的 ETW 事件，参考 `lymsiq/IPRC1000-Adapter` 的做法：
ETW 取包 → 解码 → 写虚拟声卡 → 输入法从虚拟声卡收音）。

## 已知限制

- 观察模式下，方向键 / OK 本来就会被系统当方向键和回车处理，改键后**原生行为仍会同时发生**
  （遥控器会打出一个方向键，你映射的动作再执行一次）。接管模式下没有这个问题。
- `0x17` 幽灵键在观察模式下只能被本程序忽略，打出到窗口的那个 `i` 拦不住。
- 必须保持 `run.cmd` 的窗口开着；关掉即停止映射。
- 遥控器休眠断开后，按下任意键会自动重连，映射无需重启。
- 遥控器的语音键（扫描码 `0x32`）偶尔会**只发按下、不发抬起**，甚至短时间连发几十个 down
  （实测 2 秒 30 个）。程序靠「同一键按下期间不再重复触发」和「语音动作 120 秒超时强制释放」
  兜住，正常使用察觉不到；如果发现语音动作像被按住不放，再按一次那个键让它补一个抬起即可。
